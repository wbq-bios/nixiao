# 逆水小助手 · 后端设计（微信云开发）

> 2026-10-28 制定。依据：选型总结（通用内核+游戏内容包）、原型总结 §5 数据模型、执行计划 Phase 1。
> 定位：**免运维、零自建服务器**。全文所有集合/字段/接口均带 `gameId` 维度，姊妹游戏（金铲铲等）直接复用同一套后端。

---

## 1. 总体架构

```
小程序端（原生）
  pages / components / core
    │  wx.cloud.callFunction            本地兜底：games/<gameId>/data（演示数据包）
    ▼
云开发（单环境，如 xiaqi-prod-xxxx）
  ├─ 云函数  login / content / user / vote / admin     ← 客户端只跟云函数说话
  ├─ 云数据库 11 个集合（内容 8 + 用户 3）
  └─ 云存储   分享卡片图、广告素材（预留，MVP 不用）
```

**核心原则（写代码前先记住这四条）：**

1. **客户端不直连数据库**。所有读写经云函数，openid 由 `wxContext` 服务端注入，永不信任客户端传的身份。
2. **云端字段与 `games/<gameId>/data/*.js` 演示数据完全同构**（`n/c/job/bonds` 等短键原样入库）。录入=把 JS 数组转 JSON 导入，不发明第二套字段。
3. **gameId 贯穿一切**：每个集合、每次查询、每个 _id 都含 `gameId`。多游戏共用同一个云环境，零边际成本。
4. **内容热更新走版本号短路**：客户端带 `version` 请求，没变只回几百字节，变了整包下发。赛季更新、数据勘误、广告开关全部云端生效，不发版。

## 3. 云数据库设计（11 集合）

### 3.1 内容集合（8 个，客户端只读，admin 写入）

字段即 `games/xq/data/*.js` 的结构，统一追加系统字段 `gameId`。演示数据就是录入模板。

| 集合 | 字段（演示数据同构 + 系统） | 说明 |
|---|---|---|
| `pieces` | `n, c(1-5), job, bonds[], note, hot, season, gameId` | 棋子 |
| `bonds` | `n, t(势力/职业), lv("2/3/4"), d, color(0/1), season, gameId` | 羁绊 |
| `equipments` | `n, r(白/紫/独珍/橙武), d, who, season, gameId` | 装备 |
| `augments` | `n, t(专属/转职/经济/属性), d, season, gameId` | 心悟 |
| `comps` | `n, tier(S/A/B), pop, carry, colorBond, heat, upd, main, style[], traits[], front[], back[], stats{}, eq[], aug[], beats[], tip, season, gameId` + **计数冗余 `up, down`** | 阵容；`up/down` 由 vote 云函数事务维护，列表页免聚合 |
| `odds` | `lvl, p[], season, gameId` | 刷牌概率表 |
| `seasons` | `id("S4"), name, range, current(0/1), order, gameId` | **赛季云端化**：新赛季上线=加文档+改 current，不发版 |
| `patch_notes` | `date, html, gameId` | 更新志（不分赛季，按 gameId） |

业务键约定：内容表用**确定性 _id** = `{gameId}:{season}:{n}`（patch_notes/odds 用 `{gameId}:{date}` / `{gameId}:{season}:{lvl}`）。admin 重复导入即覆盖，天然幂等。

### 3.2 用户集合（3 个，客户端禁直连）

| 集合 | _id 规则 | 字段 | 说明 |
|---|---|---|---|
| `user_sims` | 自动 _id | `openid, gameId, name, board[28], stars{}, items{}, main, season, createdAt, updatedAt` | 摆棋存档；**上限 50 条/人/游戏**，超限提示先删 |
| `user_favs` | `f:{gameId}:{openid}:{compName}` | `openid, gameId, compName, season, createdAt` | 收藏；_id 天然唯一，toggle=有则删无则建 |
| `votes` | `v:{gameId}:{openid}:{compName}` | `openid, gameId, compName, value("up"/"down"), season, updatedAt` | 一票制；**云数据库无唯一索引，用确定性 _id 做唯一约束**（add 冲突=已投票），改票=update value |

> votes 的 `_id` 内嵌 `compName` 而非 `season`：阵容名全局唯一，用户换票不受赛季切换影响；`season` 仅作记录维度。

### 3.3 配置集合

| 集合 | _id | 字段 | 说明 |
|---|---|---|---|
| `config` | `{gameId}` | `currentSeason("S4"), contentVersion(自增整数), adEnabled(bool), adUnitId, notice{text,until}` | 单文档：赛季切换、**广告开关**（原型预留的位）、弹窗公告、内容版本号 |

### 3.4 索引（控制台创建）

| 集合 | 索引 |
|---|---|
| pieces / bonds / equipments / augments / comps / odds | 复合：`gameId + season` |
| seasons | `gameId + order` |
| patch_notes | `gameId + date(倒序)` |
| user_sims | 复合：`openid + gameId + updatedAt(倒序)` |
| user_favs / votes | _id 已覆盖查询路径（按 openid 查走 `openid + gameId` 复合索引） |

### 3.5 安全规则（全部集合统一）

```json
{ "read": false, "write": false }
```

客户端一律走云函数（云函数侧调用不受安全规则限制），规则全关兜底防误配。云函数出错时前端回退本地演示数据包（§7）。

## 4. 云函数设计（5 个）

函数少而聚合（按调用次数计费，action 分发优于多函数）。所有函数统一返回 `{ ok, data, err }`，`err` 为 `{code, msg}`。

### 4.1 `login`（首启 1 次）
- 入参：无。→ 返回 `{openid}`。用途：前端缓存 openid 做调试与埋点；其余函数内部自取，不依赖它。

### 4.2 `content`（内容包下发 · 热更新核心）
- 入参：`{gameId, season?, version?}`，`debug:1` 时跳过缓存。
- 逻辑：
  1. 读 `config` 得 `contentVersion, currentSeason`；
  2. `version` 相同 → 返回 `{unchanged: true, version}`（**高频路径，几百字节**）；
  3. 否则并行读 8 个内容集合（season 缺省= currentSeason），组装：
     `{version, currentSeason, adEnabled, notice, pack: {pieces, bonds, equips, augments, comps(含up/down), odds, notes, seasons}}`。
- 缓存策略：`pack` 数组按集合做 30s 内存缓存（防同一版本被并发重复聚合）。

### 4.3 `user`（存档/收藏 CRUD + 本地数据迁移）
- 入参含 `{gameId}` + action：
  - `listSims {season?}` → 我的阵容（按 updatedAt 倒序）
  - `saveSim {name, board, stars, items, main, season}` → 结构校验（board 长=pack.board.rows×cols、stars/items 键值合法）+ 上限 50，超限回 `ERR_LIMIT`
  - `delSim {_id}` → 校验属主 openid 后删
  - `listFavs` → 我的收藏（含 compName/season）
  - `toggleFav {compName, season}` → _id 存在删/不存在建，返回收藏态
  - `myVotes` → 本人全部票向 `{compName: value}`（渲染列表页自己的票）
  - `migrate {favs[], sims[]}` → **一次性本地→云端迁移**（Phase 1 切云后首启调用，逐条导入并跳过 _id 冲突）
- 所有 action 先鉴 openid，只读写本人文档。

### 4.4 `vote`（一票制赞踩）
- 入参：`{gameId, compName, value}`，value ∈ `"up" | "down" | ""`（空=取消）。
- 逻辑（runTransaction）：
  1. votes 按 _id 查旧票 `old`；
  2. comps（按 `{gameId}:{season}:{n}`，season 由 compName 反查可得）计数：`old===new` 直接返回；否则 `up/down` 相应 ±1；
  3. 写/改/删 votes 文档。
- 防刷：同一 `_id` 两次请求间隔 <3s 回 `ERR_TOO_FAST`；value/compName 白名单校验；comps 文档不存在回 `ERR_NO_COMP`。
- 返回：`{up, down, mine}`。

### 4.5 `admin`（内容管理，仅自己用）
- 鉴权：`config.admins` 存 openid 白名单（非白名单一律拒绝并记 `admin_logs`）。
- action：
  - `import {coll, rows[]}` → 批量写内容集合（确定性 _id 覆盖式导入，幂等）
  - `bumpVersion` → `contentVersion += 1`（导入完手动/自动调）
  - `switchSeason {id}` → seasons.current 标记互换 + config.currentSeason + bumpVersion（一次搞定赛季切换）
  - `setConfig {adEnabled?, notice?, admins?}` → 广告开关/公告
- 所有操作追加 `admin_logs`（openid, action, arg, at），防误操作可溯源。
- MVP 不做管理界面：用微信开发者工具「云函数本地调试」或控制台直接调。量起来后再补一个仅 admins 可见的管理页。

### 4.6 错误码

| code | 场景 |
|---|---|
| `ERR_AUTH` | 未取到 openid（一般不会） |
| `ERR_LIMIT` | 存档超 50 条 |
| `ERR_TOO_FAST` | 投票频控 |
| `ERR_NO_COMP` / `ERR_NOT_FOUND` | 阵容/文档不存在 |
| `ERR_FORBID` | admin 非白名单、delSim 非属主 |
| `ERR_PARAM` | 结构校验失败 |

## 5. 热更新与赛季切换 SOP

**数据勘误/新阵容录入**：整理 JSON → `admin.import` → `admin.bumpVersion` → 用户下次冷启动 content 短路失效，拉新包。全程不发版。

**新赛季上线（如 S5）**：
1. `admin.import` 新赛季 6 张内容表（pieces/bonds/equipments/augments/comps/odds，season="S5"）；
2. `admin.import seasons` 加 S5 文档；
3. `admin.switchSeason("S5")`：旧赛季 current→0，S5 current→1，config 同步，version++；
4. 用户端：启动拉到新 currentSeason → seasonManager 重置到新当前赛季，图鉴/阵容/摆棋自然切到 S5 数据，旧赛季在切换器里自动变「归档」。
5. 阵容 `up/down` 计数是**赛季内**的（comps 文档按 season 分文档），新赛季从 0 开始，符合直觉。

**广告开关**（用户量达标后）：`admin.setConfig {adEnabled: true, adUnitId}` → content 下发 → 前端 ad-slot 组件由占位虚线框切真实 `ad` 组件，无需发版。

## 6. 防刷与配额

| 风险 | 对策 |
|---|---|
| 刷票/换票脚本 | openid 服务端注入；_id 唯一锁一人一票；3s 频控；compName 必须存在于 comps |
| user_sims 塞垃圾 | 50 条上限 + 结构校验（board 长度、stars 1-3、items ≤3）+ 单文档限 16KB（board/棋子名数组远小于此） |
| content 被刷 | 版本短路后单次响应几百字节、30s 服务端缓存；基础套餐调用配额内可控 |
| admin 越权 | openid 白名单 + 操作日志 |
| 敏感内容 | 全部数据自录（无 UGC），无审核风险 |

## 7. 前端接入改造（对应执行计划 1.1–1.4）

1. **app.js**：`wx.cloud.init({ env: "xiaqi-prod-xxx", traceUser: true })`（注释已留位）。
2. **新增 `core/cloud.js`**：Promise 化 `call(name, data)` + 超时（5s）+ 重试（content 1 次）；`fetchPack(gameId, season)` 带版本缓存的 content 调用，storage 键 `xq-pack-{gameId}-{season}` 存整包与 version。
3. **`core/store.js` 双轨**（键位已同构，只改此文件）：
   - `pack.cloudEnabled=false`（现状）：本地 storage + 本地演示数据，**行为完全不变**；
   - `=true`：favs/sims/votes 走 `user`/`vote` 云函数，接口签名保持现状（`toggleFav(name, season)` 等），页面零改动；首启调一次 `user.migrate` 上传本地存量。
4. **降级链**：content 失败/超时 → 用 `games/<gameId>/data` 演示数据渲染（永不白屏）；user/vote 失败 → toast「网络不佳，稍后再试」，本地不写（避免双写不一致）。
5. **pack.js**：`pack.data` 保留为兜底数据源；seasons 列表启动时用云端下发的覆盖（云端为准）。

## 8. 目录结构与部署

```
miniprogram/
├─ cloudfunctions/
│  ├─ login/     index.js, package.json（wx-server-sdk）
│  ├─ content/   index.js, package.json
│  ├─ user/      index.js, package.json
│  ├─ vote/      index.js, package.json
│  └─ admin/     index.js, package.json
├─ core/cloud.js        ← 新增
├─ core/store.js        ← 双轨改造
└─ project.config.json  ← 增加 "cloudfunctionRoot": "cloudfunctions/"
```

部署步骤：控制台开通环境（选基础套餐）→ 建 11 集合 + §3.4 索引 + §3.5 安全规则 → 开发者工具右键逐函数「上传并部署：云端安装依赖」→ `admin.setConfig` 录入自己 openid → `admin.import` 导入演示数据 JSON → 改 app.js env + `pack.cloudEnabled=true` 真机验证。

> 顺带收益：`games/jcc/`（金铲铲包）接入同一环境时，只需 `admin.import` 带 `gameId:"jcc"` 的数据 + 新小程序项目指到同一 env，5 个云函数一行不改。

## 9. 容量与费用测算（日活 1000 假设）

| 调用 | 频次估算 | 日调用量 |
|---|---|---|
| content（含版本短路） | 每次冷启动 1 次 | ~3k |
| user（listSims/listFavs/myVotes/存删） | 人均 ~6 | ~6k |
